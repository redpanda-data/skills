# connect-cdc-mysql Skill Source Map

Maps each claim in `skills/connect-cdc-mysql/SKILL.md` to the source it derives from, so syncs and
human maintainers know where to verify it. The skill is thin: it keeps only the "How to work"
procedures below, each backed by a behavioral eval case in
`evals/suites/connect-cdc-mysql.eval.json`, and sends the agent to the docs for everything else.
This file maps only the claims the skill still makes.

The `mysql_cdc` input is Go source in the **public** repo `redpanda-data/connect` under
`internal/impl/mysql/`. Its reference page is generated from the Go config spec, with an
autogenerated copy in the same repo (`docs/modules/components/pages/inputs/mysql_cdc.adoc`), and is
published at https://docs.redpanda.com/connect/components/inputs/mysql_cdc/. Read source with
`gh api repos/redpanda-data/connect/contents/internal/impl/mysql/<path>?ref=<tag>`. Verified against
tag `v4.117.0` on 2026-11-10.

## Docs gaps reported (not skill claims; do not re-verify here)

The `mysql_cdc` page is generated from the config spec, so each gap is a spec fix in
`internal/impl/mysql/input_mysql_stream.go` in `redpanda-data/connect`, checked against the
published page on 2026-11-10.

- **Table name rules** (`tables` field description). Names are checked when the input is built, not
  by a lint rule, so `rpk connect lint` passes and the pipeline fails at startup. A name has no
  database prefix, is at most 64 characters (runes), starts with an ASCII letter, `_`, or a
  character in U+0080 to U+FFFF, then may also use digits and `$`; there is no way to quote other
  names (for example one with `-`). The page says only "A list of the database table names".
  Source: `validate.go` (`validateTableName`), called from `newMySQLStreamInput`. Case
  `hyphenated-table-name`: baseline 0/3, docs 0/3, both 3/3 (pre-thin skill).
- **MySQL privileges** (component description). Streaming needs `REPLICATION SLAVE` and
  `REPLICATION CLIENT`; the snapshot needs `SELECT`, `LOCK TABLES`, and `RELOAD` or `FLUSH_TABLES`
  for its `FLUSH TABLES <tables> WITH READ LOCK`. The page's prerequisites list only MySQL 8 and
  binary logging. Source: `snapshot.go` (`buildFlushAndLockTablesQuery`) and the MySQL 8.4 `FLUSH`
  manual page. Case `snapshot-privileges`: baseline 3/5, docs 4/6 over two runs, so the docs
  search may find the grants on another page; the `mysql_cdc` reference page lacks them.
- **A stored position that no longer exists** (component description, "Snapshot and streaming
  modes"). If the binlog file in the checkpoint has been purged, the input keeps failing and
  reconnecting; it does not take a snapshot or start at the current position. The page says only
  that a restart resumes from the stored position. Source: `input_mysql_stream.go` (`Connect`,
  `startMySQLSync`). Case `purged-binlog-no-fallback`.
- **Checkpoints are file and offset, not GTIDs** (component description or `checkpoint_cache`).
  The stored position belongs to one server's binlog files, so it is not valid after a failover to
  another server, and the checkpoint must be reset. Source: `event.go` (`position = mysql.Position`,
  `binlogPositionToString`). Case `failover-checkpoint-invalid`.

## Lines removed because the baseline passed

Each case stays in the suite; the skill has no line for it.

- Backfill a table added to `tables` with a separate input and its own `checkpoint_key`, not by
  clearing the main checkpoint: `add-table-backfill-own-checkpoint`, baseline 3/3.
- Give a copied pipeline that shares a checkpoint cache its own `checkpoint_key`:
  `copied-pipeline-checkpoint-key`, baseline 3/3.
- Set `max_reconnect_attempts` low with IAM auth: `iam-reconnect-attempts`, baseline 0/3 but docs
  3/3 (it is in the `aws.enabled` description), so it is a fact the docs already carry.

The pre-thin skill's facts on snapshot locking and restarts, update row images, type mapping,
parallel snapshot workers, memory caches, licensing, GTIDs, primary keys, and failover were
covered by sampled and targeted cases; the baseline passed each one. Its Iceberg, Tiered Storage, Schema ID Validation, and FIPS
sections were broker features, documented in the Redpanda docs, and are not carried.

## TODO / re-verify

- The published page has a "Binlog rotation" section saying that on rotation Connect flushes the
  current batch and stores the new position. In source, `OnRotate` only records the new file name,
  and the checkpoint advances at transaction boundaries (`OnXID`, `readMessages`). The section is
  not in the config spec. Flag for a human to check and correct.
- The published prerequisites say "MySQL version 8 or later" while the input also supports MariaDB
  (`flavor: mariadb`). Whether MariaDB versions belong there is a product decision.
